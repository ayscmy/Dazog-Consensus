# 07 · 权限与流转矩阵

> 代码位置：角色与范围 `src/auth.js`；审批规则 `src/approval.js`；状态校验在 `src/routes/*.js`。

## 1. 角色

| 角色 | 代码 | 典型岗位 | 数据范围 | 一句话职责 |
|---|---|---|---|---|
| 系统管理员 | `admin` | IT 管理员 | 全集团 | 管账号、管组织、查审计，不参与业务审批 |
| 总经理 | `gm` | 集团总经理 | 全集团 | 看全局、批超额折扣、批大额合同 |
| 销售总监 | `director` | 事业部/公司销售负责人 | 本公司及下级 | 管团队、批 5~10% 折扣、批中大额合同 |
| 销售经理 | `manager` | 部门经理 | 本部门及下级 | 带人、批 ≤5% 折扣、第一关合同审核 |
| 客户经理 | `ae` | 销售/客户经理 | 仅本人 | 跟单、报价、推进商机、申请开票 |
| 线索专员 | `sdr` | SDR / 电销 | 仅本人 | 拓客、首触、转化线索 |
| 财务 | `finance` | 财务经理/会计 | 全集团单据 | 审账期税率、开票、登记回款、核销 |
| 法务 | `legal` | 法务顾问 | 全集团合同 | 审非标条款、违约责任 |

**为什么 SDR 与 AE 必须分开**：线索归属和商机归属是两条计量线。SDR 的产出是"有效转化数"，AE 的产出是"赢单金额"。混在一起，没人愿意做拓客这种收益不直接的工作。

## 2.1 三级组织与分级管理（v2.3）

组织按 `path` 深度分 4 层，层级写在 `org_units.level`：

| 层级 | 典型组织 | 谁能管这一层 | 能授予的角色 |
|---|---|---|---|
| 1 级 | 集团 | 系统管理员、总经理 | 管理员：全部；总经理：除管理员外全部 |
| 2 级 | 公司 | 销售总监 | 销售经理 / 客户经理 / 线索专员 |
| 3 级 | 部门 | 销售经理 | 客户经理 / 线索专员 |
| 4 级 | 团队 | 客户经理 / 线索专员 | 不可管理他人 |

规则（`src/auth.js` → `MANAGE_RULES` / `canManageUser`）：

1. 不能管理自己；
2. 不能管理管理员与总经理（管理员除外）；
3. 不能跨出自己所在组织子树——上级看下级可以，兄弟部门互相看不见；
4. 授予角色不能超过自己的管理上限（防止经理给自己人发总监权限）。

“上下级能看见”的实现：人员可见范围 = **本组织子树 + 祖先组织链**（`peopleScope`），所以经理能在通讯录里看到自己的总监，总监能看到下属经理与业务员；但业务数据仍按 `scopeFilter` 只向下看，上级的私单不会漏给下级。

## 3. 数据范围

| 范围 | 判定 | SQL 片段 |
|---|---|---|
| 全集团 | `all` | `1=1` |
| 本组织及下级 | `org` | `org_id IN (SELECT id FROM org_units WHERE path LIKE '<我的path>%')` |
| 仅本人 | `self` | `owner_id = <当前用户>` |

三处容易搞错的地方：

1. **线索的可见范围比"仅本人"宽一点**：业务员能看到"已转成自己商机的线索"，否则他不知道自己商机的来源。
2. **财务/法务是 `all` 但不是"万能"**：他们能看全部单据，但改不了商机、建不了报价——模块权限与数据范围是正交的两层。
3. **审批不受数据范围限制**：审批人只按 `approval_steps.approver_id` 判定，不看组织范围。否则跨公司代管会卡住流程。

## 4. 字段级权限

| 字段 | 可见角色 | 说明 |
|---|---|---|
| 报价单 `cost`（成本） | admin / gm / director / manager / finance | 业务员拿到 `undefined` |
| 报价单 `gross_margin`（毛利率） | 同上 | 由服务端计算后下发，业务员为 `null` |

**这条不是洁癖**：业务员能看报价金额是工作必需，但看到底价和毛利，等于把谈判底线交给对方。

实现方式是在 `GET /api/quotations` 与 `/api/quotations/:id` 里**从响应对象中删除字段**，而不是前端隐藏。

## 5. 操作权限

| 操作 | 谁能做 |
|---|---|
| 删除线索 | 经理及以上，且记录在本人范围内 |
| 删除客户 | 仅 admin，且无关联商机/合同 |
| 删除商机 | 仅 admin / gm，且无关联报价/合同 |
| 终止合同 | 总监及以上，需填原因 |
| 开票 / 作废发票 | 仅 finance / admin / gm |
| 登记回款 / 核销 | 仅 finance / admin / gm |
| 申请开票 | 合同负责人（业务员可以发起，财务执行） |
| 维护用户与角色 | 仅 admin |
| 查看审计日志 | admin / gm |
| 设置销售目标 | admin / gm / director / manager（限本人范围） |
| 查看线索公海 | 有 `lead` 模块权限者；可见范围由 `poolWhere()` 按 `org_units.path` 子树隔离。`self` 角色**看得到本组织池、看不到同组织他人私有线索**（私有线索走 `scopeFilter()`） |
| 领取公海线索 | 有 `lead` 模块权限且账号 `active`；受 `pool.hold_limit` / `pool.claim_weekly_limit` 约束；并发下用 `where owner_id is null` 条件更新，只有一个成功 |
| 主动放回公海 | 线索负责人本人；或经理及以上代本组织成员放回（需有该记录编辑权）。已转化 / 判无效不可放回 |
| 分配公海线索 | 仅 `admin/gm/director/manager`（`assertPoolManager()`）；目标必须是组织范围内在职成员；`trial` 与 `self` 角色不可 |
| 强制回收线索 | 仅经理及以上；对象须在自己可见范围内、未转化 / 未判无效；会写 `pool_events` 留痕 |
| 查看公海审计轨迹 | 有 `lead` 模块权限者，按组织树隔离 |
| 修改公共池规则 | 仅 admin（系统设置 → 公共池规则）；admin / gm 可查看 |

> 公共池**不新增模块权限**，前端导航、7 个接口统一复用 `lead`。
> `trial` 角色 `scope='org'`、只看自己那份独立试用组织，可领但不可分配 / 强制回收。
> 池中线索（`owner_id IS NULL`）禁止绕过领取直接改状态、改字段、记跟进或删除，统一返回 `POOL_NOT_IN_POOL`。
> 详见 `docs/20-公共池设计方案.md` 第 3.4 / 11.2 节。

## 6. 状态机

### 线索

| 当前 | 可变更为 | 条件 |
|---|---|---|
| new | contacted | 无 |
| new | invalid | 填原因 |
| contacted | qualified | 需求 + 预算或采购时间 + 联系电话 |
| contacted | invalid | 填原因 |
| qualified | contacted | 倒退，无额外条件 |
| qualified | invalid | 填原因 |
| qualified | converted | **走转商机接口**，四要素齐全 |

### 商机

| 当前 | 目标 | 硬条件 | 系统检查 |
|---|---|---|---|
| lead_in | needs | 需求确认、预算 | 缺则 400 + 缺项清单 |
| needs | proposal | 决策人联系人 ≥1、需求与预算已确认 | 同上 |
| proposal | negotiation | 已批准报价 | "需先走折扣审批（0% 折扣提交即通过）" |
| negotiation | won | 已生效合同 + 赢单原因 | "合同三关通过后自动赢单" |
| 任意 | lost | 输单原因 | — |

不可跳阶段；`won` / `lost` 为终态。

### 合同

| 当前 | 触发 | 下一状态 |
|---|---|---|
| draft | 提交审批 | sales_review / finance_review / legal_review（按链首节点） |
| 审批中 | 当前节点通过 | 下一节点对应的 review 状态 |
| 审批中 | 任一节点驳回 | rejected |
| 最后一关通过 | 系统自动 | **active**（同时生成回款计划、商机赢单） |
| active | 终止 | terminated |

**合同状态不能手工改为 active**，只能由审批链触发。

### 报价

`draft` →（提交）`pending` →（通过）`approved` /（驳回）`rejected` →（生成合同）`converted`。

### 发票 / 回款计划

- 发票：`applied`（待开票）→ `issued`（已开票）→ `void`（作废，需无核销记录）。
- 回款计划：`pending` → `received`，到期未收即为逾期（不落库，按 `due_date` 实时计算）。

## 7. 审批规则

### 报价折扣

| 折扣区间 | 审批链 |
|---|---|
| ≤ 5% | 部门经理 |
| 5% ~ 10% | 部门经理 → 销售总监 |
| > 10% | 部门经理 → 销售总监 → 总经理 |

### 合同

| 条件 | 审批链 |
|---|---|
| ≤ 50 万 且 账期 ≤ 30 天 | 部门经理 → 财务 |
| > 50 万 或 账期 > 30 天 | 部门经理 → 销售总监 → 财务 |
| > 100 万 或 账期 > 60 天 或 含非标条款 | 部门经理 → 销售总监 → 财务 → 法务 |

审批人由组织树向上逐级查找对应角色；**v2.3 起不再静默跳过**：提交前必须能看到每一关的具体审批人，缺人直接拦下（详见下节）。

### 审批必须"点名到人"（v2.3）

只给角色（"部门经理"）不够——申请人不知道单子落在谁手上，审批人也不知道自己该不该动。所以：

1. 提交前先调 `GET /api/approvals/preview?type=quote|contract&id=`，返回每一关的**具体审批人**（姓名 / 职称 / 组织）与**候选人列表**；
2. 前端弹「提交审批 · 确认审批人」，逐关展示；同一角色有多人时可下拉改派；
3. 提交时把 `assignees`（`{ 角色: 用户ID }`）一起带上，服务端只接受该节点的合法候选人；
4. 任一节点找不到在职审批人 → 返回 400 并列出缺失角色，提示先去组织里指定负责人，**不允许静默跳过**。

候选人排序按组织树由近及远（本部门 → 上级部门 → 集团），所以默认永远是"最直接的那位上级"。

### 决策规则

- 只有 `current_step` 上指定的审批人（或 admin）能操作。
- 驳回必须填意见。
- 通过即流转下一关；最后一关通过后回调业务（报价批准 / 合同生效）。

## 7.1 离职交接（v2.3）

账号状态：`active`（在职）→ `left`（离职）。状态由交接动作产生，**不允许直接把状态改成 `left`**。

流程（一次事务内完成）：

1. 发起人（管理员 / 上级）打开 `GET /api/admin/users/:id/handover`，看到**资产盘点**（客户 / 进行中商机 / 线索 / 合同 / 待审批单据）与**接收人候选**（本部门优先，含上级经理、总监）；
2. 勾选要交接的资产、指定接收人 → `POST /api/admin/users/:id/handover`；
3. 事务内：改 `owner_id`（客户/商机/线索/合同）、改 `org_id`、把待审批节点转给具备同角色的接收人；
4. 账号置为 `left`，写入 `left_at` / `handover_to` / `handover_at`，删除全部会话（**立即掉线**）；
5. 弹窗告知「已于某时间离职，账号已停用」，并列出交接数量；
6. 之后再登录 → 401，提示「该账号已于 2026-10-31 11:19 离职，账号已停用，无法登录。」（返回 `detail.code = 'left'`）。

补充规则：

- 至少保留一位在职系统管理员，不能把最后一个管理员交接离职；
- 接收人必须在发起人的组织链内（不跨域），且具备对应模块权限；
- 接收人没有某审批节点的角色时，该节点不转派，接口返回 `approvalLeft` 提醒管理员去审批中心改派；
- 管理员可通过 `POST /api/admin/users/:id/restore` 恢复离职账号（离职时间会被清空，审计日志留痕）。

客户转让（非离职场景）走 `POST /api/accounts/bulk-transfer`：客户列表勾选多个 → 转让给本部门同事或上级经理/总监，进行中商机可一并转移；合同、开票、回款记录不动。

## 8. 四个交接点的硬条件（速查）

| 交接 | 谁交给谁 | 必须齐备 |
|---|---|---|
| 线索转商机 | SDR → AE | 联系人姓名/职位/电话、需求描述、预算或采购时间、下一步动作与日期、商机金额 |
| 报价转合同 | AE → 经理/总监/总经理 | 价格已落定（状态 = approved）；零折扣报价提交即通过，有折扣需审批通过 |
| 合同生效 | 销售 → 财务 → 法务 | 金额 > 0、账期已填、关联报价已批准、三级审批全通过 |
| 开票与回款 | AE → 财务 | 合同已生效、开票额 ≤ 合同额 − 已开票、回款自动核销发票 |
