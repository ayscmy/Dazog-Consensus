# 08 · 部署与运维

## 1. 前置条件

| 项 | 要求 | 检查 |
|---|---|---|
| Node.js | ≥ 22.5（需要内置 SQLite） | `node -v` |
| 端口 | 默认 8081，可用 `PORT` 环境变量改 | `netstat -ano \| findstr 8081` |
| 磁盘 | 20GB 起（数据库 + 备份） | — |
| 内存 | 2GB 足够 | — |

不需要 `npm install`，没有 `node_modules`，没有构建步骤。

## 2. 三种部署形态

### 形态 A · 单机或内网（推荐起步）

```bash
cd D:\wwwroot\MSERM
npm start
```

局域网同事访问 `http://192.168.x.x:8081`。

放行端口（管理员 PowerShell）：

```powershell
New-NetFirewallRule -DisplayName "MSERM CRM 8081" -Direction Inbound -Protocol TCP -LocalPort 8081 -Action Allow
```

### 形态 B · 内网 + 域名（Nginx 反向代理）

```nginx
server {
    listen 80;
    server_name crm.example.com;

    location / {
        proxy_pass http://127.0.0.1:8081;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 60s;
    }
}
```

> 反代后要确认 `X-Forwarded-For` 传到了服务端，否则审计日志里的 IP 全是 127.0.0.1（`server.js` 已读取该头）。

IIS 方案：装 **URL Rewrite** + **ARR**，建反向代理规则指向 `http://localhost:8081`，并关闭 ARR 的"响应压缩"避免 SSE/长轮询问题（本系统无长连接，一般不受影响）。

### 形态 C · 公网访问

**必须加 HTTPS**，否则会话 Cookie 与密码明文过网。用 Nginx + Let's Encrypt（certbot）或云厂商证书：

```nginx
server {
    listen 443 ssl http2;
    server_name crm.example.com;
    ssl_certificate     /etc/letsencrypt/live/crm.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/crm.example.com/privkey.pem;
    # ... 同上 proxy 配置
}
server {
    listen 80;
    server_name crm.example.com;
    return 301 https://$host$request_uri;
}
```

公网部署还要做：
- 关闭 `admin` 默认密码，或直接禁用该账号、另建管理员。
- 在反向代理层加访问控制（IP 白名单 / VPN / 零信任网关），CRM 不适合无条件暴露公网。
- 服务本身加了登录限流（5 次失败锁 5 分钟），但挡不住分布式撞库，建议再加 WAF 或 fail2ban。

## 3. 开机自启

### Windows · 任务计划程序（推荐，无需装软件）

以管理员身份执行（把路径换成你的实际路径）：

```powershell
$action  = New-ScheduledTaskAction -Execute "C:\Program Files\nodejs\node.exe" `
           -Argument "--no-warnings server.js" -WorkingDirectory "D:\wwwroot\MSERM"
$trigger = New-ScheduledTaskTrigger -AtStartup
$settings = New-ScheduledTaskSettingsSet -AllowStartIfOnBatteries -DontStopIfGoingOnBatteries `
           -RestartCount 3 -RestartInterval (New-TimeSpan -Minutes 1) `
           -ExecutionTimeLimit (New-TimeSpan -Days 0)
Register-ScheduledTask -TaskName "MSERM-CRM" -Action $action -Trigger $trigger `
  -Settings $settings -User "SYSTEM" -RunLevel Highest
```

开机后服务自动起；进程异常退出会在 1 分钟后重启（最多 3 次）。

手动控制：

```powershell
Start-ScheduledTask  -TaskName "MSERM-CRM"
Stop-ScheduledTask   -TaskName "MSERM-CRM"
Get-ScheduledTaskInfo -TaskName "MSERM-CRM"
```

### Windows · NSSM（需要"服务"面板管理时）

```powershell
nssm install MSERM-CRM "C:\Program Files\nodejs\node.exe" "--no-warnings server.js"
nssm set MSERM-CRM AppDirectory "D:\wwwroot\MSERM"
nssm set MSERM-CRM AppStdout "D:\wwwroot\MSERM\logs\stdout.log"
nssm set MSERM-CRM AppStderr "D:\wwwroot\MSERM\logs\stderr.log"
nssm set MSERM-CRM Start SERVICE_AUTO_START
nssm start MSERM-CRM
```

### Linux · systemd

```ini
# /etc/systemd/system/mserm-crm.service
[Unit]
Description=MSERM CRM
After=network.target

[Service]
Type=simple
WorkingDirectory=/opt/mserm
ExecStart=/usr/bin/node --no-warnings server.js
Restart=always
RestartSec=3
Environment=PORT=8081
User=www-data

[Install]
WantedBy=multi-user.target
```

```bash
systemctl daemon-reload && systemctl enable --now mserm-crm
```

## 4. 备份

### 手动备份（不停服）

```bash
cd D:\wwwroot\MSERM
npm run backup
# 生成 data\backups\crm-2026-10-30T14-55-00.db
```

底层是 SQLite 的 `VACUUM INTO`，生成一致性快照，服务继续跑不受影响。

### 每日自动备份

任务计划程序，每天 02:00：

```powershell
$action  = New-ScheduledTaskAction -Execute "C:\Program Files\nodejs\node.exe" `
           -Argument "--no-warnings src/backup.js" -WorkingDirectory "D:\wwwroot\MSERM"
$trigger = New-ScheduledTaskTrigger -Daily -At 2:00AM
Register-ScheduledTask -TaskName "MSERM-CRM-Backup" -Action $action -Trigger $trigger -User "SYSTEM"
```

保留策略（删除 30 天前的备份）：

```powershell
Get-ChildItem "D:\wwwroot\MSERM\data\backups\crm-*.db" |
  Where-Object { $_.LastWriteTime -lt (Get-Date).AddDays(-30) } | Remove-Item -Force
```

### 恢复

```bash
# 1. 停服务（任务计划或 nssm）
Stop-ScheduledTask -TaskName "MSERM-CRM"

# 2. 备份现状，再覆盖
Move-Item D:\wwwroot\MSERM\data\crm.db D:\wwwroot\MSERM\data\crm.broken.db
Copy-Item D:\wwwroot\MSERM\data\backups\crm-2026-10-30T02-00-00.db D:\wwwroot\MSERM\data\crm.db

# 3. 删除残留 WAL（很重要，否则会读到旧数据）
Remove-Item D:\wwwroot\MSERM\data\crm.db-wal, D:\wwwroot\MSERM\data\crm.db-shm -ErrorAction SilentlyContinue

# 4. 启动
Start-ScheduledTask -TaskName "MSERM-CRM"
```

> 覆盖数据库前**一定删掉 `-wal` 和 `-shm`**，否则 SQLite 会用旧的 WAL 回放，看起来像"恢复失败"。

## 5. 升级

```bash
# 1. 停服务
Stop-ScheduledTask -TaskName "MSERM-CRM"

# 2. 备份
npm run backup

# 3. 替换代码（data 目录不要动）
#    把新版本覆盖到 D:\wwwroot\MSERM，保留 data\crm.db

# 4. 启动（建表语句是 IF NOT EXISTS，增量字段需手工 ALTER）
Start-ScheduledTask -TaskName "MSERM-CRM"
```

数据库结构变更没有迁移框架，目前靠 `src/db.js` 的 `CREATE TABLE IF NOT EXISTS`。**新增字段时**需要手工执行：

```sql
ALTER TABLE opportunities ADD COLUMN xxx TEXT;
```

建议把每次结构变更记在 `docs/` 下的变更日志里。

回滚：停服务 → 覆盖代码 → 用升级前的备份还原 `data\crm.db` → 启动。

## 6. 监控

**看日志**：服务前台运行时，每个 API 请求都会打一行 `方法 路径 状态码 耗时`：

```
GET /api/dashboard 200 24ms
POST /api/contracts/4/submit 200 8ms
```

`CRM_LOG=0` 可关闭（高并发时减少 IO）。

**健康检查**：

```bash
curl -s -o /dev/null -w "%{http_code}" http://localhost:8081/login.html
# 200 即正常
```

**要关注的指标**：
- 接口 P95 明显上升 → 数据量增长或磁盘慢
- `data\crm.db-wal` 持续增大 → 有长事务或未提交连接
- 审计日志出现大量 401/403 → 可能是撞库或权限配置错误

**磁盘**：`crm.db` + `crm.db-wal` + `data\backups`。10 万条商机约 40MB，备份按 30 天保留一般不超过 2GB。

## 7. 安全清单（上线前逐条过）

- [ ] **改掉所有演示账号密码**（`crm123456` 是公开的），或删除不用的账号
- [ ] `admin` 账号改名或停用，另建一个管理员账号
- [ ] 确认 `data` 目录不在 Web 根下被直接访问（本服务只托管 `public`，默认安全）
- [ ] 公网部署必须上 HTTPS
- [ ] Windows 上确认 8081 只对内网开放，公网只开 443
- [ ] 备份文件加密或放在非共享目录（里面有全量客户与合同数据）
- [ ] 定期检查审计日志（设置 → 审计日志）中的异常登录与越权尝试
- [ ] 离职人员：停用账号（自动踢掉会话），并把其名下客户/商机转交

## 8. 故障排查

| 现象 | 原因 | 处理 |
|---|---|---|
| 启动报 `Cannot find module 'node:sqlite'` | Node 版本低于 22.5 | 升级 Node |
| 端口被占用 `EADDRINUSE` | 已有实例在跑 | `netstat -ano \| findstr 8081` 找 PID 后结束，或换 `PORT` |
| 打开是空白页 | 前端 JS 报错 | F12 看 Console；常见是浏览器缓存了旧 JS，`Ctrl+F5` |
| 登录后立刻跳回登录页 | Cookie 没保存 | 检查是否用 IP 与域名混访；HTTPS 下确认没有 `Secure` 与域名不匹配 |
| 列表看不到数据 | 数据范围限制 | 确认账号的组织与角色；`admin` 能看到全量 |
| 审批中心没待办 | 当前节点不是该用户 | 看合同详情的审批链，确认卡在哪一关、审批人是谁 |
| 提交合同报"关联报价未通过审批" | 报价还在 pending | 先完成折扣审批 |
| 阶段推进报缺项 | 证据不足 | 按返回的缺项清单逐条补 |
| 页面数据不更新 | 浏览器缓存 | 静态资源有 5 分钟缓存，`Ctrl+F5` |
| 数据库文件损坏 | 断电/磁盘故障 | 用最近备份恢复；平时务必开每日备份 |

## 9. 目录与权限

```
D:\wwwroot\MSERM\
├── data\            数据库与备份，只给服务账号读写
├── public\          静态资源，可公开
├── src\             源码
├── docs\            文档
└── legacy\          1.0 存档，可删
```

服务账号（SYSTEM 或 www-data）需要对 `data\` 有读写权限，对 `public\`、`src\` 只需读权限。

## 10. 演示实例（官网「在线测试」）

官网上的「在线测试」不是另写一套前端，而是**同一个项目再起一个实例**，只是指向一份可以随时丢弃的数据库。

### 10.1 起一个演示实例

```bash
# 1) 准备一份演示库（从官网会员中心下载的安装包解压即可）
mkdir -p /srv/mserm-demo/data
unzip mserm-demo-2.6.0.zip -d /tmp/demo
cp /tmp/demo/crm.db /srv/mserm-demo/data/crm.db

# 2) 用演示模式启动（端口自定，示例 8096）
DEMO_MODE=1 \
DEMO_USER=admin \
DEMO_RESET_HOURS=24 \
DEMO_HOME=https://your-site.example.com \
CRM_DB=/srv/mserm-demo/data/crm.db \
PORT=8096 \
node server.js
```

打开 `http://<host>:8096/demo` 就会被直接签发出演示账号的会话并跳到工作台，界面上多一个「演示环境 · 24h 重置」标识。

| 变量 | 作用 |
|---|---|
| `DEMO_MODE=1` | 打开 `/demo` 免密入口；关闭时该路径 302 回登录页并提示 |
| `DEMO_USER` | 用哪个账号演示，默认 `admin`，必须在该库里存在且状态正常 |
| `DEMO_RESET_HOURS` | 只是界面上的提示数字，真正重置靠下面的换库 |
| `DEMO_HOME` | 顶栏「返回官网」的地址，留空则不显示 |

### 10.2 定期重置

演示库会被访客改得面目全非，建议每天凌晨换回原始文件：

```bash
# /etc/cron.d/mserm-demo
0 4 * * * root cp /srv/mserm-demo/pristine.db /srv/mserm-demo/data/crm.db && systemctl restart mserm-demo
```

`pristine.db` 就是最初那份解压出来的 `crm.db`，先备份一份留底。SQLite 是单文件，换库 + 重启只有几百毫秒。

### 10.3 官网那边怎么接

在**官网项目**的 `.env` 里配置：

```bash
SITE_DEMO_URL=https://demo.your-site.example.com/demo
```

首页导航、Hero 次按钮、「在线测试」区块的「立即进入演示」都会指向它；留空时按钮降级为「演示环境准备中」，不会出现死链。

### 10.4 注意事项

- 演示实例**不要**和正式实例共用数据库，也不要接真实 SMTP / 短信网关（可能在演示中被触发）。
- 演示实例建议单独子域（`demo.example.com`），方便单独限流与下线。
- `DEMO_MODE` 是公开入口，务必只开在演示实例上；正式实例保持默认关闭（未开启时 `/demo` 只会跳登录页）。
