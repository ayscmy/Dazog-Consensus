## 0. 一句话与边界

**两个池解决两件事，不能合并成一张表**：

| | A · CRM 线索公海 | B · 官网共享线索池 |
|---|---|---|
| 归属 | 一套 CRM 部署**内部** | 官网**平台侧** |
| 池里是什么 | 本企业未认领 / 超时未跟进的线索 | 运营发布的公开素材 / 演示线索 |
| 谁领 | 该企业组织内的成员 | 官网注册会员 |
| 领了之后 | `owner_id` 从 NULL 变成自己，仍在原库 | 写入会员自己的 CRM 试用组织，成为一条新线索 |
| 目的 | 线索不屯积、不流失 | 给会员持续回访理由，养到付费 |

两端通过**内部接口**单向打通（B → A），官网不直连 CRM 数据库，沿用现有 `X-Internal-Key` + 回环 IP 的模式。

## 2. 设计原则（五条，后面所有取舍都从这里推）

1. **不新增 `pool` 主表**：A 用 `leads.owner_id IS NULL` 表示「在池中」，一张表一个真相，避免池表与线索表双写不一致。
2. **池状态与业务状态正交**：不往 `status` 里塞 `in_pool`，否则会污染现有状态机（`/status`、`/convert` 的 `flow` 校验、报表按状态聚合全都要改）。
3. **规则走 `settings` 不走 `.env`**：`src/settings.js` 已有 `DEFAULTS` + `SETTING_LABELS` + 后台设置页，改规则不用重启、不用改环境，管理员自助。
4. **组织隔离沿用 `org_units.path` 前缀**：池按组织子树可见，绝不跨公司；`scopeFilter` 对 `self` 角色必须换一套 `poolWhere()`，不能复用。
5. **公海是再分配机制，不是惩罚机制**（`docs/05:304` 原话）：所有回收都留痕、可查、可申诉；**无效线索不回池**，否则池子会变成垃圾场。

## 3. A · CRM 线索公海

### 3.1 数据模型

`leads` 增 4 列（新库写进 `SCHEMA_DDL`，老库走 `COLUMN_PATCHES` 自动补）：

| 列 | 类型 | 含义 |
|---|---|---|
| `pool_at` | TEXT | 最近一次入池时间（NULL = 从未入池） |
| `pool_reason` | TEXT | 入池原因：`new` / `first_touch_timeout` / `timeout` / `release` / `reclaim` / `api` |
| `pool_count` | INTEGER DEFAULT 0 | 累计入池次数，用于统计与防刷 |
| `claim_at` | TEXT（已有） | **复用**为最近一次领取时间，不再新增字段 |

新建 `pool_events` 审计表（**不复用 `activities`**：跟进记录混杂在一起，没法统计「每周领取数」，而领取上限与转化埋点都需要可查历史）：

```
pool_events(id, lead_id, org_id, actor_id, action, reason, from_owner, to_owner, created_at)
-- action: claim | release | assign | reclaim | auto_reclaim | api_in
-- 索引: (actor_id, created_at) 供每周领取计数；(lead_id, created_at) 供轨迹回放
```

`leads.org_id NOT NULL` 保持不变：入池只清 `owner_id`，组织归属不动，池天然按组织子树隔离。

### 3.2 状态机（双时钟，正交于 `status`）

```
                    ┌────────────────── 池中 owner_id = NULL ──────────────────┐
                    │  pool_at / pool_reason 已填                              │
                    └───┬───────────────┬──────────────────┬──────────────────┘
       新建/API 推入 ───┘               │                  │
       （未指定负责人）          领取 claim / 分配 assign     │
                                       ▼                  │
                    ┌────── 私有 owner_id = X, claim_at = now ──────┐        │
                    │  status: new → contacted → qualified → converted│        │
                    └──┬──────────┬──────────┬──────────┬───────────┘        │
           手动放回 release ─┘      │      │      │                          │
           72h 无首触 ─────────────┘      │      │      判无效 invalid ──► 终止（不回池）
           30 天无有效跟进 ───────────────┘      │
           经理强制回收 reclaim ─────────────────┘
                                                  └──────────────► 回到池中
```

**两条回收时钟分开**（`docs/05` 里 24h/72h 与 30 天是两条规则，不能合并）：

| 时钟 | 起点 | 阈值 | 动作 |
|---|---|---|---|
| 首触时钟 | `claim_at` | 24h 无跟进 | 只提醒本人与经理，**不回收** |
| 首触时钟 | `claim_at` | 72h 仍无 `last_activity_at` | 回池，`pool_reason='first_touch_timeout'` |
| 跟进时钟 | `coalesce(last_activity_at, claim_at)` | 30 天无有效跟进 | 回池，`pool_reason='timeout'` |
| 保护期 | `claim_at` | 7 天内 | 屏蔽上面两条回收 |

**「有效跟进」定义**：`activities` 中 `target_type='lead'` 且 `type ∈ (call, visit, email, meeting, wechat)` 的记录；`note` 类型不算（防止写条备注就把时钟续上）。现有 `POST /api/leads/:id/activity` 已更新 `leads.last_activity_at`，只需在写入时按类型判定是否续时钟。

**修正 `docs/05`**：原图把「判无效」也画成回公海（`docs/05:108`），本方案改为**无效即终止**。理由：无效线索回池会被反复领取，稀释池子质量，也会让「领取」这个动作失去意义。

| key | 默认 | 说明 |
|---|---|---|
| `pool.enabled` | `1` | 总开关；关掉后池入口隐藏，已有私有线索不受影响 |
| `pool.auto_reclaim` | `1` | 定时回收开关（关掉仍可手动放回/强制回收） |
| `pool.first_touch_hours` | `24` | 首触提醒 |
| `pool.first_touch_reclaim_hours` | `72` | 无首触回池 |
| `pool.reclaim_days` | `30` | 无有效跟进回池 |
| `pool.protect_days` | `7` | 领取保护期 |
| `pool.hold_limit` | `50` | 单人在库上限（超出不能再领） |
| `pool.claim_weekly_limit` | `10` | 每人每周领取上限 |
| `pool.notify_before_days` | `3` | 回收前提醒 |

`SETTING_LABELS` 新增一组「公共池规则」，仅 `admin` / `gm` 可改（沿用设置页现有角色限制）。

### 3.4 接口（新增 `src/routes/pool.js`）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/leads/pool` | 池中线索，支持 `q / source / industry / org` 筛选；返回 `rows` + `stats{poolTotal, myHeld, weeklyClaimed, reclaimSoon}` |
| GET | `/api/leads/pool/rules` | 当前生效规则快照（前端展示「还能领 N 条」） |
| POST | `/api/leads/pool/:id/claim` | 领取；原子条件更新 `where id=? and owner_id is null` |
| POST | `/api/leads/pool/:id/assign` | 经理/总监分配给 `body.owner_id` |
| POST | `/api/leads/pool/:id/reclaim` | 经理强制回收他人线索回池 |
| POST | `/api/leads/:id/release` | 本人（或经理）主动放回池中 |
| GET | `/api/leads/pool/events` | 审计轨迹，`lead_id` 或 `actor_id` 过滤 |

> **坑（历史上踩过）**：`/api/leads/:id` 会吃掉 `/api/leads/pool`。`src/routes/index.js` 里 `import './pool.js'` **必须排在 `import './leads.js'` 之前**，否则池接口全部落到「线索不存在」。之前 `/api/internal/trial/ping` 被 `:id` 吃掉是同一个问题。

**领取必须做成原子操作**，不能「先查再改」：

```
update leads set owner_id=?, claim_at=?, pool_count=pool_count, updated_at=?
 where id=? and owner_id is null
```

用受影响行数判断是否抢到（SQLite `changes` / PG `rowCount`），并发两个请求只有一个成功。领前还要一次性校验：模块权限、组织可见性、在库上限、每周上限、账号状态（`frozen` 不可领）。

### 3.5 权限矩阵（对齐 `src/auth.js` 的 `ROLES`）

| 动作 | admin / gm (`all`) | director / manager (`org`) | ae / sdr (`self`) | trial (`org`) | finance / legal |
|---|---|---|---|---|---|
| 查看公共池 | 全集团 | 本组织子树 | **本组织池**（非他人私有） | 自己试用组织 | ✗ |
| 领取 | ✓ | ✓ | ✓ | ✓ | ✗ |
| 放回自己的 | ✓ | ✓ | ✓ | ✓ | ✗ |
| 分配给他人 | ✓ | ✓ | ✗ | ✗ | ✗ |
| 强制回收他人 | ✓ | ✓ | ✗ | ✗ | ✗ |
| 改规则参数 | ✓ | ✗ | ✗ | ✗ | ✗ |

**关键实现点**：`scopeFilter()` 对 `self` 返回 `owner_id = 自己`，对池中线索永远为假。必须新增 `poolWhere(user)`：`all` → `1=1`；`org` / `self` → 一律 `org_id IN (SELECT id FROM org_units WHERE path LIKE ?)`（用 `user.orgPath + '%'`）。`self` 角色**能看到本组织池，但看不到同组织其他人的私有线索**——这是刻意的，不是权限漏洞。

`trial` 角色 `scope='org'`（`src/auth.js:38-43`），天然只能看到自己那份独立试用组织的池子，与「每人独立空组织」的隔离约定完全一致。

### 3.6 定时回收（`src/pool.js`）

- `startPoolJanitor()` 在 `server.js` 与 `startTrialJanitor()` 并列注册（`server.js:184-185` 附近），**每小时跑一次**，与试用 janitor 同频。
- 每轮扫描：`owner_id IS NOT NULL` 且 `status NOT IN ('converted','invalid')`，按 3.2 的两条时钟判断；保护期内跳过。
- 回池动作：清 `owner_id`、写 `pool_at` / `pool_reason` / `pool_count+1`、写 `pool_events`、写一条 `activities(type='note')` 留痕。
- 提前 `pool.notify_before_days` 天：写提醒 `activities` + 工作台角标。**通知表当前不存在**，站内信 / 邮件 / 短信提醒列为 P2，不阻塞一期。
- 启动横幅打印当前规则摘要（与 `TRIAL_DAYS` 横幅同处），便于运维核对。

### 3.7 外部线索 API 衔接（A 的主要入口）

`src/routes/leads-api.js:73-88` 的 `resolveOwner()` 现在「没配默认负责人就抛错」。改为：

- 请求带 `owner_id` → 校验后挂给该人（现状不变）
- 未带、接入方有 `owner_id` → 用默认负责人（现状不变）
- **未带且无默认负责人** → 不再报错，改为**入公共池**（`owner_id=NULL`, `pool_at=now`, `pool_reason='api'`, `pool_events(action='api_in')`）
- 接入方新增开关 `pool_on_missing`（默认 `1`）；显式设 `0` 时保留旧的报错行为，向后兼容
- `api_clients` 加一列 `pool_on_missing`；后台「API 接入」表单加勾选项

这样第三方 / 官网推来的线索天然沉淀到公共池，由团队领取，而不是卡在「没配负责人」上。

### 3.8 试用联动与「养用户 → 收费」钩子

1. **示例数据入池**：`src/trial.js` 的 `seedSampleData()` 现预置 5 条线索且全部 `owner_id=userId`。改为 **3 条归自己、2 条入池**（`owner_id=NULL`, `pool_at=now`, `source='示例'` 不变）。用户第一分钟打开「公共池」就有可领的东西，领取 → 跟进 → 转商机一路能走通，这是比「看静态示例」更强的一次 Aha 时刻。
2. **D1 邮件话术**：`docs/19` 的 D1 增加一句「公共池里有 2 条待领取的示例线索，先领一条试试」。**邮件总数仍 5 封，不新增**（`docs/19:208` 刻意克制）。
3. **团队台阶（转化核心）**：单人试用只能「自己领」。点「分配给同事」时，若组织内仅 1 人 → 提示「添加同事一起用，社区版 10 人以内免费」并跳用户管理；添加第 11 人时由 `src/edition.js` 的 `userQuota()` 触发额度提示并跳 `UPGRADE_URL`（`https://aioffice.aiemy.com/?from=crm#pricing`）。**公共池是把「一个人用」推成「一个团队用」的第一级台阶**，而团队人数正是收费分界线。
4. **冻结态**：`frozen` 账号禁止领取与写入（登录已被 `src/auth.js:271` 拦住），池不受影响；付费恢复后原数据（含池中线索）原样回来。

## 4. B · 官网共享线索池

### 4.1 定位（**待确认，见第 9 节**）

推荐**一期做「公开素材 / 演示线索池」**，不做真实商业线索分发：

- 池里是运营发布的**脱敏、虚构或公开征集**的行业需求条目，会员领取后一键写入自己的 CRM 试用组织，作为持续的上手素材
- 每人每天限领 N 条（默认 3），领完给「升级解锁更多」入口 → `#pricing`
- 真实商机池涉及线索来源授权、脱敏、同一线索被多人领取的冲突、以及个人信息合规，需要运营与法务先就绪，列为二期

**明确不动官网现有 `leads` 表**：它是注册时写入、供我方后台销售跟进的线索（`src/db.js:319`），与「会员可领的资源」语义相反，混用会污染后台销售列表。B 另建两张表。

### 4.2 数据模型（官网 `src/db.js`）

```
pool_items(id, title, company, industry, region, demand, budget,
           contact, contact_masked, source, level, status, published_at, created_at)
-- status: published | offline；contact_masked 对外只显示脱敏值
pool_claims(id, item_id, member_id, trial_id, crm_lead_id,
            status, created_at)
-- status: delivered | failed；UNIQUE(item_id, member_id) 防重复领
-- 索引: (member_id, created_at) 供每日额度计数
```

`pool_items` 由后台「管理后台 → 线索池维护」录入，不做自动采集（资讯采集模块已按用户要求删除，不恢复）。

### 4.4 与 CRM 的内部投递（B → A 唯一通道）

CRM 侧 `src/routes/trial-api.js` 新增：

```
POST /api/internal/trial/:id/pool-lead
```

- 沿用 `X-Internal-Key` + `timingSafeEqual` + 回环 IP，路由 `{ auth: false }`
- 入参：`{ title, company, industry, region, demand, budget, contact, contactPhone, source }`
- 校验：该 `trial_accounts` 存在且 `status='active'`；`frozen` / `revoked` 一律拒绝（返回明确 code，官网据此提示「账号已冻结，恢复后继续」）
- 动作：往该试用组织 `insert into leads(...)`，`owner_id = 试用用户`，`source = '官网公共池'`，`pool_at`/`pool_reason` 不填（**它是私有线索，不进 CRM 公海**），返回 `lead_id`
- 幂等：官网带 `claim_id`，CRM 侧按 `external_id = 'pool:<claim_id>'` 去重（`leads` 已有 `uq_lead_external` 唯一索引）

> 这条边界要写死：**官网池是「平台发给会员的素材」，CRM 公海是「企业内部再分配」**。会员领到的线索直接归他私有，不进 CRM 公海，否则会出现「刚领到就被别人抢走」的荒谬体验。

## 7. 验证要点（写进 `scripts/pool-check.mjs`）

1. **并发领取**：两请求同时领同一条，恰好一个成功，另一个返回「已被领取」
2. **组织隔离**：A 公司看不到 B 公司池线索；`self` 角色看得到本组织池、**看不到**同组织他人私有线索
3. **trial 隔离**：试用账号只看到自己试用组织的池，不能分配、不能强制回收
4. **双时钟**：刚领取（保护期内）不被回收；72h 无首触回池；30 天无有效跟进回池；`note` 不续时钟
5. **无效不回池**：`status='invalid'` 的线索永远不出现在池中
6. **限额**：在库 50 条 / 每周 10 条触顶后领取被拒，文案明确
7. **老库补列**：SQLite 与 PG 各跑一次 `migrate()`，`ensureColumns()` 幂等，`select *` 不丢列
8. **路由顺序**：`/api/leads/pool` 不被 `/api/leads/:id` 吃掉
9. **官网投递**：领取后 CRM 确实多一条 `source='官网公共池'` 的私有线索；`frozen` 账号被拒且官网提示正确；`claim_id` 重放不产生重复线索
10. **SEO**：官网 `seo-check` 全过，新页在 sitemap / llms 中
11. **回归**：CRM 既有 25/25、官网 20/20、试用两端状态机对齐（14 天 / 30 天不变）

## 8. 埋点指标（补进 `docs/19` 第 6 节）

| 指标 | 算法 | 期望 |
|---|---|---|
| 池激活率 | 领取过公共池的试用账号 / 开通数 | 与「激活率」并列看，> 40% 说明池有吸引力 |
| 二次回访 | 官网连续 ≥2 天有领取的会员数 | 衡量「养用户」是否成立 |
| 团队化信号 | 试用组织内成员数 ≥2 的占比 | **最靠近收费的先行指标** |
| 授权触发 | 第 11 人提示曝光 → 跳定价点击 | 直接衡量转化 |
| 池健康度 | 池中超 7 天未被领取的条数占比 | 过高说明池子没人要，要调素材或额度 |

前四项沿用 `docs/19:196` 的说明：**目前无事件表**，一期用 `pool_events` + `pool_claims` 直接统计，不必另建看板；看板仍列为 P0 待办。

## 9. 风险与待确认（不擅自替你决定）

| # | 事项 | 建议 |
|---|---|---|
| 1 | **官网池的内容定位**：公开素材/演示线索池（推荐一期） vs 真实商业线索池 | 后者需线索来源授权、脱敏、同一线索多人领取的冲突规则、个人信息合规声明，建议二期且先出运营规范 |
