# 17 · 商业授权方案

> 目标：社区版免费限 10 人，商业授权解除限制。授权**离线可验证**，客户内网部署也能用。

## 1. 先划清边界

这套方案是**防君子不防小人**。必须先把这句话说在前面，否则后面全是自欺：

| 能防 | 防不了 |
|---|---|
| 客户手改配置把自己变成「不限人数」——不行，得验签 | 客户把 `edition.js` 里那段限制代码删掉——**Node 源码部署，改代码就能绕过** |
| 客户把授权码里的 `users` 改成 999——不行，签名会挂 | 客户用调试器在运行时改内存 |
| 一套授权码发给 3 个客户——加了机器绑定可以拦 | 彻底破解（要混淆 + 服务端心跳，成本高一个量级） |

所以定位是：**让正规客户走正规流程有据可依，让授权成为合同的一部分**，而不是技术上的绝对锁定。
真要做强防护，另立项目：代码混淆、核心逻辑下沉服务端、许可心跳。

## 2. 为什么用非对称签名

| 方案 | 产品端要有什么 | 客户能否自己签发 | 结论 |
|---|---|---|---|
| 配置里写个密码 `LICENSE_KEY=xxx` | 一个字符串 | 能，看一眼源码就知道 | ❌ |
| 对称 HMAC（签名密钥内置） | 密钥 | **能**，密钥必须随产品分发 | ❌ |
| **Ed25519 非对称签名** | **公钥** | 不能，签不出新码 | ✅ 采用 |
| 在线激活（回调服务器） | 网络 + 服务端 | 不能 | 客户内网常常无外网，❌ |
| 硬件加密狗 | 实体设备 | 不能 | 成本与物流不可接受，❌ |

非对称的关键性质：**能验不能签**。公钥嵌在代码里，客户反编译只能拿到公钥；
私钥只在 AIEMY 手里，产线机器上都没有。

选 Ed25519 而不是 RSA：签名 64 字节（授权码短很多）、验签快、Node 内置 `node:crypto` 直接支持，无需依赖。

## 3. 授权码长什么样

```
<base64url(JSON 载荷)>.<base64url(Ed25519 签名)>
```

一行纯文本，约 250–400 字符，可以直接贴进 `.env` 或后台输入框。签名覆盖整个载荷，
改动任何一个字节（包括把 `users` 从 10 改成 999）验签都会失败。

### 载荷字段

| 字段 | 必填 | 说明 |
|---|---|---|
| `v` | ✅ | 授权格式版本，当前 `1`。将来换算法用版本位并存，不会把老授权打死 |
| `id` | ✅ | 授权编号，如 `AUTH-20261101-XXXX`，对账用 |
| `to` | ✅ | 被授权方名称，后台会原样显示，写公司全称 |
| `edition` | ✅ | 版本标识：`commercial` / `pro` / `enterprise` |
| `users` | ✅ | 在职用户上限；**`0` = 不限** |
| `expire` | ⬜ | 到期日 `YYYY-MM-DD`，按当天 23:59:59 算；留空 = 永久 |
| `issued` | ✅ | 签发日期，仅做记录，不参与校验 |
| `machine` | ⬜ | 机器指纹；留空 = 不绑机器（换服务器无需重签） |
| `features` | ⬜ | 预留的附加能力列表，当前不影响任何判定 |

示例载荷（解码后）：

```json
{
  "id": "AUTH-20261101-8K2M",
  "to": "苏州精工机械有限公司",
  "edition": "commercial",
  "users": 30,
  "expire": "2027-11-01",
  "issued": "2026-11-01",
  "machine": "50194A56C1C7",
  "features": [],
  "v": 1
}
```

## 4. 密钥管理（最要紧的一节）

| 项 | 位置 |
|---|---|
| 私钥 | `C:\Users\Administrator\.aiemy-license\private-key.pem`（**仓库外**） |
| 公钥 | 已硬编码在 `src/license-core.js` 的 `PUBLIC_KEY_PEM` |
| 生产自用授权 | `C:\Users\Administrator\.aiemy-license\prod-self.license` |

三条铁律：

1. **私钥永远不进 Git、不进产品包、不发邮件**。它只在这台签发机上。
2. **丢了私钥** = 以后签不出新授权（已发出的仍有效）。请离线备份到 U 盘 / 密码管理器。
3. **换了密钥对** = 必须同时改 `PUBLIC_KEY_PEM` 并重新发版，**所有已发授权立即失效**。
   除非怀疑泄露，否则别换。

生成新密钥对（只在首次或轮换时做）：

```bash
node scripts/license.mjs keygen          # 默认写到 ~/.aiemy-license/
# 会打印公钥 → 粘贴替换 src/license-core.js 里的 PUBLIC_KEY_PEM
```

## 5. 签发

```bash
# 标准商业授权：30 人，一年期，绑机器
node scripts/license.mjs issue \
  --to "苏州精工机械有限公司" \
  --users 30 \
  --expire 2027-11-01 \
  --machine 50194A56C1C7

# 不限人数，永久，不绑机器（自家的、或战略客户）
node scripts/license.mjs issue --to "某某集团" --users 0

# 校验一张码（也可以传文件）
node scripts/license.mjs verify ./xxx.license

# 查本机指纹（客户要绑机器时，让他跑这条把结果发你）
node scripts/license.mjs machine
```

签发完工具会**自检一次**（用同一套 `verifyLicense`），自检不过就不输出——避免发出打不开的码。

`--out 文件` 可以把码同时写进文件，便于归档。建议按 `AUTH-<客户简称>-<日期>` 命名。

## 6. 生效顺序与判定

```
CRM_LICENSE（.env）  >  后台激活（数据库 settings.license.code）  >  CRM_USER_LIMIT/CRM_EDITION  >  社区版 10 人
```

- **验签失败/过期/绑错机器 → 一律当「无授权」处理**，回落下一级，不会让实例起不来；
- 后台展示具体原因（「已于 2027-11-01 到期」「绑定的是另一台机器」），便于客户自助排查；
- 授权结果缓存 30 秒，避免每个请求都验签；
- 环境变量的授权**在后台不可移除**（重启会覆盖回去），后台会提示去改 `.env`——避免「后台删了但不生效」的困惑。

### 额度怎么算

只数 **在职、且不是试用账号** 的用户：

```sql
select count(*) from users u
 where u.status = 'active'
   and not exists (select 1 from user_roles r where r.user_id = u.id and r.role = 'trial')
```

- 离职、停用不占名额 —— 否则客户每年换一批人，额度几下就被历史账号吃满；
- 试用账号不占名额 —— 它们由官网注册自动创建，算进去会让「注册即开试用」在第 N 个访客时静默失败。

## 7. 客户怎么激活

两条路，任选：

**A. 后台激活（推荐，普通客户）**

系统设置 → 商业授权 → 粘贴授权码 → 激活。存在数据库里，重启不丢，也能在界面上看到到期日。

**B. 写 `.env`（推荐，容器化/自动化部署）**

```env
CRM_LICENSE=eyJpZCI6IkFVVEgt...
```

重启后生效。适合用 Ansible / K8s / 镜像固化配置的场景。

## 8. 常见场景怎么办

| 场景 | 做法 |
|---|---|
| 客户换服务器 | 授权**没绑机器**就直接用；绑了机器要重签一张（把新指纹给签发方） |
| 客户要加人（30 → 50） | 重签一张 `users=50`，到期日不变，覆盖旧的即可。旧码作废与否不重要，反正客户只会用新的 |
| 续期 | 重签一张新到期日，其余不变 |
| 一个客户多套环境（生产+测试） | 各发一张，编号区分；或测试环境用社区版（10 人够） |
| 客户想先试后买 | 发 `users=0, expire=<30天后>` 的临时授权，到期自动回落社区版，不用你去回收 |
| 授权被客户转发给别人 | 加 `machine` 绑定；但注意这会让换机变得麻烦，按客户配合度决定 |
| 客户说「授权无效」 | 让他把后台的报错原因发你：签名失败=码抄错/被改；到期=续期；机器不匹配=重签 |

## 9. 前端的表现

- **系统设置 → 商业授权**：状态徽标、被授权方、编号、人数上限、有效期、绑定机器、来源（env/后台）、本机指纹（一键复制）；
- 未激活时显示原因与当前社区版用量（「最多 10 个在职用户，已用 8 个」）；
- 只有系统管理员能看这块（总监/经理连接口都是 403）；
- **用户管理页**：超限时顶部黄色告警条 + 新增按钮直接弹升级说明（含官网链接）。

## 10. 已知限制

| 限制 | 说明 |
|---|---|
| 时钟回拨可延长有效期 | 本地校验无法感知。要堵得靠服务端心跳，成本不划算 |
| 源码可改 | 见第 1 节。正式对外发行可考虑打包成单文件 + 混淆 |
| 授权码较长 | Ed25519 已比 RSA 短很多；`.env` 单行放得下 |
| 不支持「按模块授权」 | `features` 字段已预留，但当前没有模块级开关。要做需先在代码里定义模块边界 |

## 11. 运营建议

1. **授权编号规则**：`AUTH-<客户简称>-<YYYYMMDD>-<序号>`，和合同号对得上，年底对账省事。
2. **到期前 30 天提醒**：签发时记下到期日，日历里建提醒。技术上也可以让实例在后台显示「还有 N 天到期」——需要的话我加。
3. **不要给永久授权当默认**：默认一年期，续费是持续收入；永久授权只给战略客户或一次性买断。
4. **私钥离线备份**：至少两份，一份密码管理器、一份物理介质。
