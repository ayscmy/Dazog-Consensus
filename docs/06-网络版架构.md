# 06 · 网络版架构

> 本文描述 v2.0 的技术实现。1.0 单机原型的设计权衡见 [[01-设计思路]]。

## 1. 为什么重写而不是改造

1.0 是「整库读进内存 → 改完整体写回 JSON」的模式，代码约 1200 行。它对三个新需求是结构性不支持的：

| 需求 | 1.0 的障碍 |
|---|---|
| 多人同时在线 | 两个浏览器同时改一条记录，后写的覆盖先写的 |
| 角色与数据范围 | 没有用户概念，前端拿到的是全量数据，无法按人裁剪 |
| 字段级权限 | 数据全量下发到浏览器，成本、毛利在前端藏不住 |
| 审批流转 | 没有服务端状态机，审批链无法保证顺序与权限 |

这三条都不是加几个接口能解决的，所以保留交互与视觉资产，重写数据层与服务层。

**复用下来的**：设计变量与组件样式（`public/css`）、表格/看板/抽屉的交互范式、字段字典与枚举（演进成 `src/dict.js`）。

## 2. 技术选型

| 选择 | 理由 | 代价 |
|---|---|---|
| Node 22 内置 `node:sqlite` | 零依赖、单文件、支持事务与索引，`npm install` 都不需要 | 仍是实验特性（启动加 `--no-warnings`） |
| 原生 `http` + 自写路由 | 30 个接口不值得引入框架；路由表 40 行就能覆盖 | 没有中间件生态，需自己写鉴权/限流/审计 |
| 服务端 `scrypt` | 抗 GPU 爆破，Node 内置，无需 bcrypt 编译 | 单次约 40~60ms，登录稍慢（可接受） |
| Cookie + 服务端会话表 | 可直接踢人（改角色、停用账号时删会话） | 需要 sessions 表与续期逻辑 |
| 前端原生 ESM + hash 路由 | 无构建、无 node_modules，改完刷新即生效 | 没有组件框架，视图用模板字符串拼 |
| SQLite WAL | 读写并发不互相阻塞，单机足够几十人 | 单写者，跨机部署需换库 |

部署前提只有一条：**Node ≥ 22.5**。

## 3. 分层与请求链路

```
浏览器
  │  GET /app.html            GET /api/opportunities?stage=needs
  ▼                              ▼
server.js ── 静态文件 ──┐   ┌── API 分发 ────────────────────────┐
                        │   │ 1. 路由匹配（方法 + 路径 + :id）    │
                        │   │ 2. 会话校验（Cookie → sessions）    │
                        │   │ 3. 读取用户（角色 / 组织 / 范围）    │
                        │   │ 4. 解析 JSON（Content-Type 校验）   │
                        │   │ 5. 业务处理器（routes/*.js）        │
                        │   │ 6. 写审计（非 GET 自动记录）        │
                        │   └──────────────┬────────────────────┘
                        │                  ▼
                        │        auth.js  数据范围 → SQL 片段
                        │        approval.js 审批链 → 业务状态
                        │                  ▼
                        └────────────► db.js（SQLite / 事务）
```

关键约定：

- **处理器只返回对象**，序列化与状态码由 `http.js` 统一处理；业务错误抛 `HttpError(status, message, detail)`。
- **`detail` 承载"为什么不让你过"**。前端把它渲染成缺项清单，这是本系统体验上最有价值的一处细节。
- **非 GET 请求自动落审计**，密码字段自动剔除，不需要每个接口手写日志。

## 4. 认证与会话

```
登录：POST /api/auth/login
  ├─ 限流：同一 IP + 账号 5 次失败锁 5 分钟
  ├─ 校验：scrypt(password, salt) 定时安全比较
  ├─ 建会话：32 字节随机 token → sessions 表，12 小时有效
  └─ 下发：Set-Cookie: crm_sid=...; HttpOnly; SameSite=Lax; Path=/
```

- 剩余有效期不足 6 小时自动续期，活跃用户不会中途掉线。
- **改角色、停用账号、改密码都会删除该用户全部会话**——权限变更立即生效，不依赖 token 过期。
- CSRF：`SameSite=Lax` + 只接受 `application/json`（跨站表单无法伪造该 Content-Type），不额外引入 token。
- 密码策略：最少 8 位。生产环境建议在 `auth.js` 的 `changePassword` 里追加复杂度校验。

## 5. 权限模型：三层收口

### 第一层 · 功能权限（能不能进这个模块）

```js
ROLES = {
  admin:    { scope: 'all', modules: ['*'] },
  gm:       { scope: 'all', modules: ['dashboard','lead','account','opportunity','quotation','contract','finance','approval','report'] },
  director: { scope: 'org', modules: [... 'approval','report','team'] },
  manager:  { scope: 'org', modules: [...同上] },
  ae:       { scope: 'self', modules: ['dashboard','lead','account','opportunity','quotation','contract','approval','report'] },
  sdr:      { scope: 'self', modules: ['dashboard','lead','account','report'] },
  finance:  { scope: 'all', modules: ['dashboard','contract','finance','approval','report'] },
  legal:    { scope: 'all', modules: ['dashboard','contract','approval'] },
}
```

多角色取并集；数据范围取最宽（`all > org > self`）。

### 第二层 · 数据范围（能看到谁的数据）

组织树用**路径前缀**表达层级，避免递归查询：

```
org_units.path
  北辰集团        /1/
  ├ 华东公司      /1/2/
  │ ├ 销售一部    /1/2/3/
  │ └ 销售二部    /1/2/4/
  └ 华南公司      /1/5/
```

```js
scopeFilter(user, { owner: 'op.owner_id', org: 'op.org_id' })
// all  → 1=1
// org  → op.org_id IN (SELECT id FROM org_units WHERE path LIKE '/1/2/%')
// self → op.owner_id = 6
```

一个字符串前缀就完成了"本人 / 本部门 / 本公司 / 全集团"四种范围，查询走 `idx_org_path` 索引。新增组织、调整层级不需要改任何查询。

列表、详情、汇总、报表全部复用同一个 `scopeFilter`，不存在"列表过滤了但详情没过滤"的漏口。

### 第三层 · 字段级（同一行里哪些字段不能看）

```js
// 报价详情：业务员看不到成本，也就看不到毛利
if (!['admin','gm','director','manager','finance'].includes(user.role)) {
  delete q.cost;
  q.gross_margin = null;
}
```

**在服务端删除字段**，不是前端隐藏。这一条决定了谈判底线不会随 F12 泄露。

### 记录级写权限

```js
canEditRecord(user, rec) // all → true；org → 记录组织在本人子树；self → 记录的 owner 是本人
```

## 6. 审批引擎

### 规则（代码即制度）

```js
// 折扣
chainForDiscount(rate):
  ≤5%        → [经理]
  5%~10%     → [经理, 总监]
  >10%       → [经理, 总监, 总经理]

// 合同
chainForContract({ amount, paymentTerms, nonStandard }):
  [经理]
  + 总监   当 金额 > 50 万 或 账期 > 30 天
  + 财务   始终
  + 法务   当 金额 > 100 万 或 账期 > 60 天 或 非标条款
```

### 审批人解析

不维护"谁批谁"的配置表，而是**沿组织树向上找对应角色**：

```
申请人在 销售一部 /1/2/3/
  manager  → 查 /1/2/3/ 有没有 manager    → 王敏
  director → 查 /1/2/3/ → /1/2/ → /1/  → 李强（华东公司）
  gm       → 查到 /1/ 才找到总经理张伟
  finance/legal → 业务部门找不到，全局兜底（财务中心、法务部）
```

人员调动只改 `users.org_id`，审批路由自动跟着变；找不到审批人的节点标记 `skipped` 并写明原因，不会卡死流程。

### 状态推进

```
approvals.status: pending → approved / rejected
approval_steps:  seq 1..n，只有 current_step 的 approver 能决策
decide() 在事务里完成：
  ① 校验当前节点与审批人
  ② 写决策（结论 / 意见 / 时间）
  ③ 还有下一节点 → current_step+1；否则 status=approved
  ④ 回调业务：报价置 approved；合同置 active + 生成回款计划 + 商机自动赢单
```

第 ④ 步是"制度落地"的关键：**合同生效这件事只能由审批链触发**，没有接口可以手动把合同改成 active。

## 7. 状态机

### 线索

```
new ──触达──► contacted ──确认──► qualified ──转化──► converted
 │               │                   │
 └──────┬────────┴───────────────────┴──► invalid（必须填原因）
```

转商机前置条件（服务端逐条校验，缺失项一次性返回）：

- 联系人：姓名、职位、电话
- 需求描述
- 预算 或 采购时间
- 下一步动作 与 日期
- 商机金额 > 0

### 商机

```
lead_in ─► needs ─► proposal ─► negotiation ─► won
   │         │         │            │
   └─────────┴─────────┴────────────┴──► lost
```

| 目标阶段 | 硬条件 |
|---|---|
| needs | 需求确认 + 预算情况 |
| proposal | 需求与预算已确认 + 客户下至少 1 位"决策人"联系人 |
| negotiation | 存在**已通过审批**的报价单 |
| won | 存在**已生效**合同 + 赢单原因 |
| lost | 输单原因 |

同时禁止跳阶段：只能进入下一阶段（`lost` 除外）。

## 8. 事务与并发

- 所有跨表写入走 `tx()`：`BEGIN IMMEDIATE` → 业务 → `COMMIT`，异常回滚。`IMMEDIATE` 立即取写锁，避免两个请求同时升级锁导致死锁。
- WAL 模式：读不阻塞写，写不阻塞读。适合"多数人在看、少数人在改"的 CRM 场景。
- 单进程单写者，写操作串行；配合 `busy_timeout=5000` 兜住瞬时争用。
- 金额与数量用 `REAL`/`INTEGER`，对账比较用 `Math.abs(diff) < 0.01` 容差。

## 9. 前端结构

不用框架、不用构建：

```
app.js      外壳：拉 bootstrap、渲染侧栏与顶栏、hash 路由、视图懒加载
  └ views/*.js   每个视图导出 render(el, route, ctx)
api.js      fetch 封装（401 自动跳登录，错误统一抛出）
store.js    当前用户/组织/字典 + can() 模块判断
ui.js       esc / money / date / badge / modal / drawer / toast / 审批链
icons.js    内联 SVG 图标
```

- 路由形如 `#/opportunities?view=board` / `#/deals/12`，详情页可直接分享链接。
- 视图按需 `import()`，首屏只加载仪表盘。
- 所有渲染走模板字符串 + `esc()` 转义，避免 XSS。
- 用户能做什么由 `state.user.modules` 决定，服务端仍然二次校验（前端只是不显示按钮，不承担安全职责）。

## 10. 容量与性能

当前形态的实测边界（普通 4 核 8G 服务器）：

| 指标 | 量级 |
|---|---|
| 数据量 | 十万级记录无压力（SQLite 单表千万行仍可索引查询） |
| 并发 | 几十人同时在线，写操作串行不成瓶颈 |
| 接口耗时 | 列表 5~20ms，仪表盘 20~40ms，登录 50~80ms（scrypt） |
| 单文件体积 | 10 万条商机约 40MB |

超出这个量级（上百人并发、跨地域、需要读写分离）时的改造路径见下一节。

## 11. 演进路径

**第一步（不改架构）**
1. 消息通知：审批待办推企微/邮件，复用 `pendingFor()`。
2. 附件：合同扫描件存磁盘 + `attachments` 表，注意做权限校验后再发文件。
3. 导入导出：Excel 用流式解析，逐行过与页面相同的校验函数，保证入口一致。
4. 公海规则：定时任务扫描 N 天无跟进的线索/客户，清空 owner 并记录回收日志。

**第二步（换存储）**
5. SQLite → PostgreSQL：`db.js` 是唯一改动点，SQL 基本兼容，需处理 `julianday`、`group_concat` 等方言。
6. 多实例部署：会话从表里迁到 Redis，文件走对象存储。

**第三步（拆服务）**
7. 审批引擎抽出独立服务（它已经是纯函数 + 两张表，边界清晰）。
8. 报表走只读副本，避免大查询影响录入。
