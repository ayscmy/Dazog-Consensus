# 19 · 试用转化设计：怎么养用户，再把他变成付费用户

> 一句话：**试用不是"给个账号让他自己看"，而是一条被设计过的路——每一步都在降低
> 他放弃的理由，并且在最后一步之前，绝不让他觉得"投入白费了"。**

本文回答三件事：现在哪里不合理、改成什么样、改完怎么判断有没有用。

---

## 1. 先看原设计的漏斗

改之前是这么设计的：

```
注册 100%
  → 自动开试用 100%        ← 这块做得对：零摩擦，注册即成
  → 首次登录 ?
  → 录入第一条真实数据 极低  ← 空组织 + "会删"的心理暗示
  → 跑通报价/合同   更低    ← 7 天跑不完一个周期
  → 到期                  数据物理删除
  → 付费                  接近 0
```

### 三个断点，一个比一个致命

| # | 断点 | 机制 | 后果 |
|---|---|---|---|
| ① | **空组织** | 开通时只预置 4 个产品，其余全空 | 第一分钟看不到任何"业务"，必须自己录 |
| ② | **7 天太短** | 期限 < 一个完整销售周期 | 还没形成使用习惯就到期 |
| ③ | **到期即删** | `purgeTrialAccount()` 清 17 张表 | 用户知道"录了也会没"，于是不录；到期毫无留恋 |

②③ 是耦合的：**正因为"会删"，7 天才显得更短**。用户不是没时间，是没动机。

### 还有三处缺位

- **零触达**：SMTP 未配置，注册后 7 天没有任何邮件
- **无价值时刻**：没有引导，用户不知道"发出第一份报价"才是这个系统的核心动作
- **无承接**：只有「7 天试用 → 商业授权」两档，中间没有落脚点；而社区版当时写的是
  「仅个人学习、禁止商用」，把"想正经用但只有三五个人"的客户直接推走了

## 2. 改后的链路

```
注册
 ├─ 立刻可用：示例数据已就位（3 客户 / 5 线索 / 2 商机 / 1 报价）
 │    → 第一分钟就能看懂"线索 → 商机 → 报价"长什么样
 ├─ D1 邮件：别急着录入，先改示例
 ├─ D3 邮件：报价单可以直接发链接给客户（制造 Aha 时刻）
 ├─ D6 邮件：还剩 8 天，建议录 3 个真实单子
 ├─ 14 天到期 → 冻结（账号只读、数据完整保留）
 ├─ D12 邮件：先说清楚"数据会留着"，消除焦虑
 ├─ D14 邮件：已到期，但东西都在，怎么恢复
 ├─ 冻结期 30 天 → 付费即时恢复原数据
 └─ 30 天后仍无动作 → 真正回收
```

关键差别不在功能，在**每一步都给了继续的理由**。

---

## 3. 五个改动，各自解决什么

### 3.1 示例数据：把"第一分钟"填满

开通时预置一套完整但虚构的业务：

| 对象 | 数量 | 作用 |
|---|---|---|
| 客户 | 3 | 打开客户列表就不是空的 |
| 线索 | 5 | 覆盖 new / contacted / qualified / converted 四种状态，能看懂状态流转 |
| 商机 | 2 | 一条在"方案"阶段（有报价入口），一条在"需求"阶段 |
| 报价 | 1 | 草稿状态，含明细，可以直接看报价单长什么样 |

标记方式：统一 `source = '示例'`，界面上显示为「来源：示例」，用户按来源筛出来就能批量删。
不用隐藏字段——**让用户明确知道哪些是样例，比假装是他的数据更诚实**。

> 实现：`crm-local/src/trial.js` 的 `seedSampleData()`，失败不阻断开通。

### 3.2 14 天：够跑完一个周期

7 天的问题不是"短"，是**短于一个决策周期**。一个真实销售从"愿意试"到"敢往里录客户"，
通常需要 3~5 天；剩下 2 天根本来不及走完报价→合同。

14 天能给到：3 天熟悉 + 5 天录入 + 5 天跑流程 + 1 天做决定。

### 3.3 冻结代替删除：这是转化率的关键改动

| | 旧 | 新 |
|---|---|---|
| 到期动作 | 清 17 张表 → 删用户 → 删组织 | `users.status='frozen'` + 保留全部数据 |
| 用户能登录吗 | 不能（账号没了） | 不能（只读/禁登录） |
| 数据还在吗 | **不在了** | **在，保留 30 天** |
| 付费后 | 从零开始 | 原样恢复 |
| 邮件话术 | "到期会自动删除" | "已为你保留 30 天" |

**为什么这一条最重要**：它同时解决了两个问题——
① 用户敢录真实数据了（因为不会消失）；② 到期时他有理由回来（因为东西还在里面）。

沉没成本不是坏事，它是"我在这上面投入过"的自然延伸。旧设计把它清零了。

> 实现：CRM `freezeTrialAccount()` / 官网 `freezeTrial()`，两边状态机对齐。

### 3.4 邮件序列：在快忘掉的时候出现一次

D1 / D3 / D6 / D12 / D14，五封。原则：

- **每封只推一个动作**，不堆功能清单
- **只发最新那封**：服务停三天再起来，不会把积压的 5 封一次性全发出去
- **未配 SMTP 不写发送记录**：配好后该补的还会补
- 语气是"有事说事"，不写"亲爱的用户"，不用感叹号

| 步骤 | 主题 | 目的 |
|---|---|---|
| D1 | 别急着录入，先看这套示例数据 | 降低第一动作的门槛 |
| D3 | 报价单可以直接发给客户看 | 制造价值时刻（Aha） |
| D6 | 试用过半，还剩 N 天 | 制造进度感，催录入 |
| D12 | 还有 N 天，数据会一直给你留着 | 提前消除"会删"的焦虑 |
| D14 | 试用已到期，数据已为你保留 30 天 | 给恢复路径 |

> 实现：`AIOffice.aiemy.com/src/trial-mails.js`，随 janitor 每小时跑一次。

### 3.5 免费档承接：别把中间层推走

许可从「仅个人学习、禁止任何商业用途」改为 **「10 个在职用户以内可免费自用，含经营用途」**。

原因很直接：真正会付费的，往往是"先用起来、人变多了才需要授权"的团队。
如果免费档连"自己公司日常用"都不允许，这批人根本不会开始。

新的边界很清楚：

| 场景 | 社区版 | 商业授权 |
|---|---|---|
| 自己公司用，≤10 人 | ✅ 免费 | ✅ |
| 自己公司用，>10 人 | ❌ | ✅ |
| 作为服务卖给第三方 / 交付客户项目 | ❌ | ✅ |
| 代运维、SaaS、付费支持 | ❌ | ✅ |

> 实现：`LICENSE` v2.0、官网 `#pricing`、README、`docs/13`。

## 4. 状态机（两端必须一致）

```
       注册
        │
        ▼
     active ──到期──▶ frozen ──满 30 天──▶ revoked
        │              │
        │              └──付费──▶ active（数据原样恢复）
        │
        └──会员主动结束──▶ revoked（立即回收，不可恢复）
```

| 状态 | 能登录 | 数据 | 界面文案 |
|---|---|---|---|
| `active` | ✅ | 完整 | 剩余 N 天 |
| `frozen` | ❌ | **完整保留** | 已到期 · 保留 N 天 |
| `revoked` | ❌ | 已清空 | 已结束 |

**一致性约束**：官网只有在 CRM `freeze` 调用成功后才把自己标成 frozen。
否则会出现"官网说冻结了、CRM 还能登录"的分裂状态——这比不冻结更糟。

## 5. 参数

| 参数 | 位置 | 默认 | 说明 |
|---|---|---|---|
| `TRIAL_DAYS` | CRM `.env` | 14 | 试用天数 |
| `TRIAL_RETAIN_DAYS` | CRM `.env` | 30 | 冻结后保留天数 |
| `SITE_TRIAL_DAYS` | 官网 `.env` | 14 | 必须与 CRM 一致 |
| `SITE_TRIAL_RETAIN_DAYS` | 官网 `.env` | 30 | 必须与 CRM 一致 |
| `CRM_UPGRADE_URL` | CRM `.env` | `https://aioffice.aiemy.com/?from=crm#pricing` | 额度用尽时的跳转地址 |

> 两端天数**必须一致**。不一致的后果：官网显示还剩 12 天，CRM 已经把人冻了——
> 用户会认为系统坏了。改动时请一起改。

## 6. 怎么判断有没有用

改完之后不要只看"注册数"。看这五个：

| 指标 | 怎么算 | 期望 |
|---|---|---|
| **激活率** | 登录过的试用户 / 开通数 | 应 > 60%（有示例数据后应明显高于改前） |
| **深度使用率** | 有 ≥1 条自建线索（非示例）的试用户 / 开通数 | 这是真正的分水岭 |
| **到期留存** | 冻结时数据里仍有自建记录的账号数 | 有真实数据 = 有转化可能 |
| **公共池：单人 → 团队** | 试用组织里出现「第 2 个用户领取 / 被分配公海线索」的账号数 / 开通数 | 公海天然要求多人协作；出现领取/分配，说明试用从「一个人试试」变成「团队在用」，是付费授权最强的**前置信号** |
| **恢复率** | 冻结后 30 天内付费恢复 / 冻结总数 | 这是最终指标 |

前四个是过程指标，能提前两周告诉你"这批试用有没有希望"。

> 为什么加「公共池」这一条：试用组织默认是「每人独立空组织」，一个人用得再深也只需要 1 个账号；
> 一旦组织里出现第 2 个人去公海领线索，就必然要加成员、要分配、要团队数据隔离——
> 而社区版许可的上限正是「10 个在职用户」，这条路径直接指向授权购买。
> 数据源已有：`pool_events(action='claim'|'assign')` 按 `actor_id` 与 `org_id` 即可统计，无需另埋点。
> 一期公海已实现，见 `docs/20-公共池设计方案.md`。

> 目前这些数还没有埋点，只有 `trial_accounts` 的原始记录可以人工统计。
> 要做成看板需要加事件表，见 `docs/09-演进路线与待办.md`。

## 7. 已知取舍

1. **示例数据占存储**：每个试用账号多约 10 行数据，量级可忽略（< 20KB/账号）。
2. **冻结期占用组织树**：frozen 账号的组织仍在「试用中心」下，最长 30 天。
   迁移到 PG 后如果试用量大，可以按 `frozen_at` 建索引加快扫描。
3. **冻结后不能自助恢复**：目前恢复要走人工（付费后由管理员改状态）。
   做成"输入授权码即恢复"需要把 license 校验接到 trial 流程里，属于下一步。
4. **邮件只有 5 封**：刻意克制。发太多会进垃圾箱，也显得急于成交。
5. **没有 A/B 能力**：话术和天数都写死在配置里，换文案要改代码。量小时不值得做实验框架。
