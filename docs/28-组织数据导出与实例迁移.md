# 28. 组织数据导出与实例迁移（P1-B）

> 适用版本：CRM 2.11+ · 状态：已落地（本地）· 首期仅支持 SQLite 目标库

## 1. 要解决的问题

商业化链路里，注册会员先进入**试用共享实例**（多组织共用一个库），付费后由实例编排器拉起**独立实例**（每客户一个数据目录、一个 SQLite 库、一个进程）。

在 P1-B 之前，付费客户拿到的是一个空实例：试用期间录入的客户、线索、商机、报价、合同、回款、审批、跟进记录全部带不过去。这个断点直接影响客户是否愿意付费。P1-B 补的就是「试用共享 → 付费独立实例」的组织级数据迁移通道。

## 2. 边界：官网不碰数据

| 角色 | 职责 | 不做什么 |
|---|---|---|
| 官网（8099） | 会员、套餐、订单、确认收款、调用 CRM `tenant/activate` 把试用组织转正、记录订阅台账 | **不读 CRM 数据库、不接触快照文件、不参与数据搬运** |
| CRM 共享实例（8081） | 保存试用组织业务数据；`activate` 把 `trial_accounts` 转正并写 `tenants.org_id` / `instance_state=pending` | — |
| CRM 编排器（`provision:tenant`） | 建独立实例库与管理员、**导出试用组织快照、导入独立实例库**、回写迁移状态 | — |
| CRM 独立实例 | 承载付费客户业务数据，独立库、独立进程 | — |

迁移完全发生在 CRM 侧。官网只负责「确认收款 → 开通租户」，编排器负责「建实例 → 搬数据」，两层互不越界。这也是为什么官网仓库在 P1-B 里**零改动**。

### 2.1 完整触发链

```
会员下单 → 官网 confirmPaid → CRM POST /api/internal/tenant/activate
   ├─ trial_accounts: active → converted
   ├─ users / user_roles: 试用角色转正
   └─ tenants: 新增一行，org_id = 试用组织 id，instance_state = 'pending'
                                  migration_state = 'pending'
        ↓（运维或定时任务执行 npm run provision:tenant -- --all-pending）
CRM 编排器 provisionTenant(code)
   ├─ init-tenant.mjs：建目录 / 独立库 / 根组织 / admin / 租户 .env
   ├─ exportOrg(tenants.org_id)：从共享库导出业务快照（当前进程连的就是共享库）
   ├─ seal → 加密快照落盘到 <租户目录>/migration/org-snapshot.json
   ├─ org-import.mjs 子进程：CRM_DB 指向独立实例库，导入
   ├─ rm 加密快照（成功即删，避免业务数据长期留盘）
   └─ tenants: instance_state='provisioned'、migration_state='done' + 备注
        ↓（scripts/tenant-ctl.mjs start）
独立实例启动，客户在独立实例里看到试用期全部业务数据
```

## 3. 快照格式契约（`src/org-snapshot.js`，纯逻辑）

| 字段 | 含义 |
|---|---|
| `format` | 固定 `mserm-org-snapshot` |
| `version` | `1` |
| `exportedAt` | ISO 时间 |
| `source` | `{ orgId, orgName, engine }` |
| `tables` | 固定 21 张业务表的数据，每张为行数组 |
| `counts` | 每表行数 |
| `checksum` | `sha256(format + version + orgId + 规范化后的全部表数据)` |

**校验和规范化**：`canonicalTables()` 按 `TABLE_ORDER` 固定表序输出，不受对象键顺序影响，可跨语言复算；`assertSnapshot()` 会校验 format / version / 表齐全 / checksum，任一不符即拒绝导入。

**加密落盘**：`seal()` / `unseal()` 用 AES-256-GCM，`key = sha256(passphrase)`，IV 与 tag 随包携带；`readSnapshotFile()` 自动识别明文/密文并做校验。明文快照只在内存中存在。

### 3.1 表清单

按 `org_id` 直接过滤（9 张）：
`accounts, approvals, contracts, leads, opportunities, pool_events, products, quotations, targets`

按主外键路径收敛（8 张）：
`contacts, quotation_items, quote_sends, payment_plans, invoices, payments, payment_allocations, approval_steps`

按源组织用户 id 过滤（4 张）：
`activities, attachments, audit_logs, handovers`

**不进快照**（`EXCLUDED_TABLES`）：
`org_units, users, user_roles, sessions, settings, tenants, trial_accounts, api_clients, api_logs, contract_templates`

三个需要特别说明的排除项：

- **用户与组织不迁移**。目标实例已有自己的根组织与管理员；快照里的 `org_id` 统一重映射到目标根组织，用户引用列统一重映射到目标管理员。
- **`api_clients` 不迁移**。它是官网签发的名录对接凭据（`directory_token` / `directory_tier` / `key_hash`），与实例绑定；复制到独立实例会出现两个实例共用同一令牌。独立实例如需对接名录，由官网重新签发。
- **`contract_templates` 不迁移**。它是全库内置模板（`migrate()` 会预置），不属于组织业务数据；目标实例初始化后自带。

### 3.2 导出边界为什么收紧

早期设想用 `contract_id IN (...) OR account_id IN (...)` 捞回款，会把别的组织挂在同一客户下的回款一起带出来，破坏租户隔离。现在 `FK_RULES` 只走主键路径：先确定组织内主表行，再按这些行的 id 向内收敛关联表。`payments` / `invoices` 只按组织内 `contracts.id` 集合过滤。

## 4. 导入规则（`src/org-transfer.js`）

| 规则 | 实现 |
|---|---|
| 目标库限制 | `DB_ENGINE !== 'sqlite'` 直接 400；PostgreSQL 明确报错，不静默降级 |
| 目标必须为空 | 遍历 `TABLE_ORDER`，任一表 `count(*) > 0` 即 409 拒绝覆盖 |
| 幂等 | `settings` 写入 `org_transfer.snapshot = checksum`；同 checksum 重入返回 `already: true, rows: 0` |
| 组织重映射 | 所有 `org_id` → 目标根组织 id |
| 用户重映射 | `USER_REF_COLS` 命名集合 + `pragma foreign_key_list()` 动态补集（凡是 `REFERENCES users(id)` 的列自动纳入），全部 → 目标管理员 id。避免手写集合漏列留下悬空引用 |
| 去重 | `DEDUP_KEYS`：`targets` 有 `UNIQUE(user_id, period)`，多用户同周期在重映射后会撞唯一约束，按重映射后的键去重跳过 |
| 循环引用 | `opportunities.contract_id ↔ contracts.opportunity_id` 无法拓扑排序；事务内临时 `PRAGMA foreign_keys=OFF`，导入完成恢复 |
| 引用完整性 | 导入后跑 `PRAGMA foreign_key_check`，把违规条目原样返回给编排器写入 `migration_note`，**不静默吞掉** |
| 目标缺组织/管理员 | 自动补建根组织与 `admin`（随机 12 字符密码，随返回值一次性给出） |

导入按 `TABLE_ORDER` 顺序逐表逐行插入，显式带上原 `id`（目标库为空，不会冲突）；列名用 `pragma table_info()` 过滤，快照里多出的列自动忽略，便于旧版本快照导入新版本库。

## 5. 编排器接线（`src/tenant-provision.js`）

`provisionTenant(code)` 在 `init-tenant.mjs` 成功之后、实例启动之前调用 `migrateOrgData()`：

- `tenants.org_id` 为空（新客无试用数据）→ `migration_state = 'skipped'`。
- 有试用组织 → 先标 `running`，导出 → 加密落盘 → 子进程导入 → 成功后删除快照并标 `done`；**失败只标 `failed` 并保留加密快照供排查，不把整个实例判死，也不吞异常**。
- 已 `provisioned` 的租户重跑编排时，若 `migration_state ∈ {pending, failed, running}` 且实例**未启动**，会自动重试迁移；实例处于 `running` 时不碰它的库文件（避免与运行中的进程抢锁）。

> 迁移必须在实例启动前完成。若需要给已运行的实例补迁数据，先 `tenant:ctl stop`，再重跑 `provision:tenant --code=...`。

### 5.1 台账字段

`tenants` 新增两列（DDL 与 `COLUMN_PATCHES` 均有，老库自动补列）：

- `migration_state`：`pending | running | done | skipped | failed`
- `migration_note`：导入行数、去重跳过行数、外键待核对数、checksum；失败时记错误摘要

`GET /api/internal/tenant/usage` 与 `tenant/activate` 等接口的 `viewOf()` 已暴露 `migrationState` / `migrationNote`，官网如需展示迁移进度可直接读取，无需新增接口。

## 8. 已知边界与风险

1. **跨组织引用可能悬空**：例如共享实例里来自名录同步的 `leads.contact_id` 指向其它组织的联系人。出于数据隔离考虑，导出不会跨组织补全，迁移后这类引用会悬空；导入后 `PRAGMA foreign_key_check` 会把它们列出并写进 `migration_note`，需人工核对。**宁可暴露，不静默改数据，也不越界取数**。
2. **首期仅 SQLite**：独立实例默认单文件 SQLite；PostgreSQL 目标库请用备份/恢复工具，代码里明确报错而非降级。
3. **快照体量**：快照整体读入内存并整体落盘。组织数据量很大时需评估内存与磁盘，必要时改流式分片（P2）。
4. **口令管理**：快照加密口令当前复用实例管理员密码（编排器生成、AES 密文存 `tenants.admin_password`）。生产环境建议改用独立的迁移密钥，并与实例管理员密码分离。
5. **实例启停时序**：迁移只在实例启动前执行；对已运行实例补迁必须先停服。
6. **业务规则数据不迁移**：`settings`、`contract_templates`、`api_clients` 等平台/全局配置不随组织走，独立实例按自身初始化结果为准。
