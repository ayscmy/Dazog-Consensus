# 01 · 设计思路

> ⚠️ 本文档描述 **1.0 单机原型**（JSON 文件存储、无登录）。当前版本为 2.0 网络版，请优先阅读 [[06-网络版架构]] · [[07-权限与流转矩阵]] · [[08-部署与运维]]。

## 1. 需求是怎么落到"自建一套"的

原始需求只有一句："部署一套 ATTIO，"。这句话至少有三种可能的意思，先拆开：

| 可能的意思 | 可行性 | 结论 |
| --- | --- | --- |
| 部署 Attio 官方产品 | 不可能。Attio 是纯 SaaS，官方不提供私有化版本 | 排除 |
| 自托管 Attio 的开源替代（如 Twenty） | 需要 Docker Compose（Postgres + Redis + 后台 worker） | 本机无 Docker，短期内不可行 |
| 做一套 Attio 形态的 CRM 并跑起来 | 有 Node 22，零依赖即可实现 | **采纳** |

确认环节给出的两个答案决定了范围：

- 运行形态：**只做本地可运行的版本**（不接云数据库、不发布公网）；
- 功能优先级：**三大对象 + 表格视图（筛选排序）+ 看板拖拽**，明确排除"自定义字段"。

于是范围被锁死为：单人、单机、三类数据、两种视图、一个详情面板。

## 2. 一个关键判断：不要把 Attio 当"功能清单"抄

Attio 的核心不是"有表格和看板"，而是三件事：

1. **对象（Object）是第一公民**：公司、人、商机共用同一套表格/筛选/详情交互，只是字段不同；
2. **记录是活的**：点开一条记录不是弹窗，而是侧边抽屉，改完即存，不打断当前列表上下文；
3. **视图可复用**：同一份数据，表格看结构、看看板看流程。

所以实现时优先保证"三类对象共用一套渲染器"，而不是给每个对象写一套页面。`OBJECTS` 配置对象是整个前端的核心——加一个新对象（比如"工单"）只需要加一段配置，表格、筛选、抽屉、关联列表全部自动可用。

## 3. 技术选型与取舍

### 3.1 不引入框架（React/Vue）

- **考虑过**：Vite + React + 组件库，工程化更"正规"。
- **选择**：原生 JS + 模板字符串渲染。
- **理由**：单机小应用，引入框架就要 `node_modules`、构建步骤、版本升级；而这个应用的所有界面都是"列表 + 表单"，用 `innerHTML` 重渲染完全够用，且**任何人拿到源码双击就能看懂**。代价是复杂交互需要手写，且重渲染粒度需要自己控制（见 3.4）。
- **何时该换**：当出现嵌套 3 层以上的组件状态、或需要撤销/重做时，应迁移到框架。

### 3.2 服务端只用 Node 内置模块

- **考虑过**：Express、Fastify、lowdb。
- **选择**：`node:http` + `node:fs`。
- **理由**：需要的能力只有"发静态文件"和"读/写一个 JSON"，用 Express 属于用牛刀；而 `npm install` 在离线或内网机器上经常是第一个失败点。零依赖意味着**克隆即可运行、永不被供应链问题影响**。
- **代价**：路由、MIME、请求体解析、路径穿越防护都得自己写（约 180 行，见 `server.js`）。

### 3.3 存储用整库 JSON，而不是 SQLite

- **考虑过**：SQLite（`better-sqlite3` 需要编译原生模块，Windows 上常失败）。
- **选择**：单个 `db.json`，PUT 整库回写。
- **理由**：
  - 数据量：几百到上千条记录，JSON 约几十 KB，整库读写毫无压力；
  - 可运维性：出问题直接打开文件就能看、能改、能复制备份，不需要任何工具；
  - 无迁移成本：表结构变化 = 前端配置变化，不需要写 migration。
- **代价**：
  - 并发写会互相覆盖（单用户场景可接受）；
  - 数据量到 10 万条级别会明显变慢——**那时必须换 SQLite**；
  - 写入用"写临时文件 → rename"保证原子性，避免断电留下半截 JSON。

### 3.4 渲染粒度：为什么搜索不整页重渲染

第一版是所有输入都触发 `render()` 全量重绘。问题在中文输入法：

- 输入拼音时，输入框正在 composition 状态，一旦被 `innerHTML` 替换，候选词直接丢失，打不出字。

所以搜索改成"只重渲染 `#results` + 手动更新计数"，输入框 DOM 节点保持不变。抽屉里的字段输入同理：**输入事件只写数据 + 防抖落盘，不重渲染**；只有"公司 / 联系人 / 阶段"这类会改变选项列表或关联区块的字段，才在变更后重绘抽屉。

这是一个通用的教训：**任何会打断用户输入的重渲染都是 bug，不是性能问题。**

### 3.5 详情用抽屉而非弹窗

Attio 的做法是右侧抽屉，理由是"看详情时不该丢失列表上下文"。代价是抽屉宽 520px，会遮住表格右侧——但列表仍在，滚动位置不丢，关闭即回到原处。这一条被直接沿用了。

抽屉里的字段没有"编辑模式"：输入框常驻，无边框、悬停才显出背景，聚焦才出现高亮环。这样既保持"看起来像详情"，又做到"点一下就能改"。

### 3.6 看板拖拽用原生 HTML5 DnD

- **考虑过**：`SortableJS` 之类的库（能做出插入位置指示线）。
- **选择**：原生 `draggable` + `dragover`/`drop`。
- **理由**：需求是"拖到某列改阶段"，不涉及列内排序，原生 API 20 行就能实现；引入库还要处理它自己的 DOM 结构约束。
- **代价**：没有"拖到第 3 张卡片前面"这种精细落点，也没有触摸屏支持（移动端需另行实现）。

### 3.7 ID 与时间

- ID 用 `c_` / `p_` / `d_` 前缀 + 随机串，前缀让肉眼能分辨记录类型，也方便调试时直接改 JSON。
- 日期一律存 `YYYY-MM-DD` 字符串，避免时区问题；`createdAt` 由前端生成，`meta.updatedAt` 由服务端在每次写入时打时间戳。

## 4. 视觉方案

- 中性色骨架：`#fafaf9` 侧栏 / `#ffffff` 主区 / `#e8e8e5` 描边，让数据本身是唯一的高对比元素。
- 单一强调色 `#2f6bff`，只用在三处：主按钮、选中态、筛选条件。强调色一多，界面立刻变廉价。
- 行高 42px、字号 12.8px、表头 11.5px——密度接近 Attio，一屏能看到 15 行左右。
- 表格首列 `position: sticky`，横滚时对象名称始终可见。
- 头像/图标用名字哈希生成稳定色（`hsl(h, 40%, 93%)`），不引入图片资源，零网络请求。

## 5. 交互细节清单

| 细节 | 动机 |
| --- | --- |
| 点击表头循环 升序 → 降序 → 取消 | 少一个"清除排序"的按钮 |
| 筛选条件以 chip 常驻显示 | 避免"为什么列表是空的"这种困惑 |
| 新建记录立刻落到列表首位并打开抽屉 | 符合"先创建再补充"的真实习惯 |
| 删除公司时级联清空联系人与商机的公司字段 | 不留悬空引用，避免出现"孤儿记录" |
| 换公司时若原联系人不在新公司，自动清空联系人 | 防止出现"商机属于 A 公司、联系人属于 B 公司"的脏数据 |
| `⌘K` / `Ctrl+K` 聚焦搜索，`Esc` 关抽屉 | 键盘可达性 |
| 深链接 `#/deals/d1` | 便于分享定位、也便于自动化测试直接截图 |
| 看板列头显示条数与金额合计 | 销售看板真正关心的两个数字 |

## 6. 故意没做的事

| 没做 | 原因 | 真要做的话 |
| --- | --- | --- |
| 登录与权限 | 单机单人，加了只是形式主义 | 引入用户表 + session，记录级 `owner` 过滤 |
| 自定义字段 | 需求确认时明确排除；且会牵动表格列配置、表单渲染、筛选器三处 | 字段定义进 `meta.schema`，渲染全部走配置 |
| 附件 / 富文本备注 | 需要文件存储与编辑器，收益低 | 本地 `uploads/` + 文件字段 |
| 全文检索 | 当前是逐条 `includes`，千条内无感 | 建倒排索引或换 SQLite FTS |
| 移动端适配 | 表格 + 看板在手机上体验天然差 | 单独设计卡片式列表视图 |
| 变更历史 / 撤销 | 需要事件溯源 | 每次写入追加 `events.jsonl` |

## 7. 演进路径（如果要从单机走向团队）

1. **换存储**：`db.json` → SQLite（保留同样的 REST 语义，前端零改动）；
2. **加认证**：`/api/*` 前挂 session 中间件，`meta.me` 改为登录用户；
3. **改增量**：`PUT /api/db` 拆成资源级接口（`POST /api/companies` 等），避免并发覆盖；
4. **加实时**：SSE 推送变更，多人同时编辑不打架；
5. **上公网**：此时才需要反代（IIS / Nginx）+ HTTPS，见 [[03-运维部署]] 第 5 节。
